**主线一句话：**

| ③ 抢票那一秒，存储怎么分工 | 100s | NoSQL 键值存储判资格、消息队列缓冲、关系型数据库落库、扣减带条件兜底、集合去重 | 全部用存储口径讲，不用「原子性/Lua」这类词 |

**为什么这样挂得住题：** 老师选题要的是「存储技术怎么选、怎么分工」。我们的答案很干净——**热数据（库存、已购名单、登录凭证）放 NoSQL 键值存储，冷数据（订单）放关系型数据库，中间用消息队列缓冲写入**。这就是专题里「分布式数据库、NoSQL/NewSQL」讲的混合存储形态，不需要扯别的。

## 1.2 讲稿·主讲版（约 5 分钟，可直接念）

> **【① 开场 · 约 40 秒】**
> 老师好，我们组选的是专题四「大数据存储」的第 4 项，分布式数据库和 NoSQL/NewSQL。我们没做概念综述，而是做了一个能跑起来的演出票务抢票平台，叫 TicketHub，**现在已经部署在服务器上，打开浏览器就能访问**。
> 这次汇报，我重点讲这个平台的**存储层**：哪些数据放在哪里、为什么这么放、抢票那一秒存储是怎么分工的。
>
> **【② 用户视角走一遍 · 约 75 秒】**
> 先看用户能干什么。打开首页，是演出分类和演出列表，每张卡片有海报、名称、场馆、时间和最低票价。点进一场演出，能看到这场演出的所有票档，比如内场、看台、VIP，每个票档后面跟着**当前余票**。登录用手机号加验证码，演示环境验证码直接显示在页面上。登录后选票档点「立即抢购」，页面提示抢票成功并给出订单号。进「我的订单」能看到这笔订单并支付，个人中心还能每日签到。
> 这六个功能里，**有两个和存储直接相关**：一个是「余票」，它必须在开票瞬间被高频读写；一个是「订单」，它必须长期保存、不能丢。**这两类数据的要求完全不一样，所以我们在存储上把它们分开了。**
>
> **【③ 抢票那一秒，存储怎么分工 · 约 100 秒，核心段】**
> 我把抢票这一秒拆成四步，对应四种存储角色。
> **第一步，判断资格——用 NoSQL 键值存储。** 用户点抢票，系统先去缓存里看两样东西：这个票档还有没有余票，这个用户是不是已经买过了。余票是一个计数值，已购用户是一个集合，这两种结构在键值存储里都是现成的，读写都在内存里，**开票那几秒几百人同时点也扛得住**。
> **第二步，缓冲写入——用消息队列。** 资格判断通过的请求，不直接去写数据库，而是先放进队列，然后马上告诉用户「抢票成功，订单号是多少」。用户不用等数据库写完，**数据库也不会被瞬时流量冲垮**。
> **第三步，落库——用关系型数据库。** 后台有消费者从队列里一条条取，把订单真正写进订单表，同时把数据库里的库存减一。订单要长期保存、要按用户查列表、要对账，**这是关系型数据库擅长的，也是它该待的地方**。
> **第四步，兜底——数据库扣减带条件。** 减库存的时候加一个「库存大于零才允许减」的条件。这样即使前面判断有偏差，也绝不会把库存扣成负数，**从机制上保证不超卖**。
> 另外还有一条规则：**一个人同一个票档只能买一张**。这个是在键值存储里用一个「已购用户集合」实现的，买过的用户 ID 记进去，下次再来直接被拦下。
> 这套流程我们做过并发测试：200 个请求同时抢 50 张票，最后**正好 50 单成功，库存归零，没有超卖，也没有一个人抢到两张**。
>
> **【④ 分工与心路 · 约 60 秒】**
> 这个项目四个人分工：一个人负责前端页面和交互，一个人负责后端演出、票档、订单这些业务接口，一个人负责抢票这条核心链路和部署上线，一个人负责数据初始化、测试和文档。**但分工不是各干各的**，每周对一次接口，对不上当场改。
> 中间有三个节点印象比较深。第一个是**一开始想得太简单**，以为抢票就是查一下库存减一，后来发现并发下会超卖，才把资格判断挪到缓存里。第二个是**订单显示零元**，查出来是后台写订单时没带票价，补上就好。第三个是**部署到服务器**，本地正常，上去页面能开但接口报错，最后发现是数据库初始化脚本没传上去，库是空的。**这几个坑踩完，才明白「能跑」和「能用」的区别。**
>
> **【⑤ 做到哪、边界在哪 · 约 25 秒】**
> 目前平台已经上线，完整链路都能走通，不超卖也验证过了。**边界也说清楚**：缓存和数据库都是单机，没做高可用，这是课程阶段的取舍；支付是模拟的，没对接真实渠道。下一步会考虑推荐、搜索和更大的并发支撑。谢谢老师，欢迎提问。

> 主讲版约 1300 字，正常语速 4 分 50 秒左右。**超时就砍 ② 里签到半句和 ④ 里第三个坑；③ 的四步一步都不能砍。**

# 四、应付老师提问的提示

## 4.1 高概率（存储与业务类）

**Q：你们这个和「分布式数据库、NoSQL」什么关系？**
> 关系就在存储分工上。**余票、已购名单、登录凭证这些热数据放在 Redis 这种 NoSQL 键值存储里**，因为开票瞬间要高频读写；订单放在 MySQL 关系型数据库里，因为要长期保存、要查列表。**两者不是替代，是分工，这就是专题里讲的混合存储。**

**Q：为什么余票不放 MySQL？**
> 开票那几秒几百人同时读写余票，放关系库会变成大量行锁竞争，请求排队。放键值存储里是内存操作，快得多。**订单最终还是要落关系库，余票只是判断资格。**

**Q：抢票具体怎么保证不超卖？**
> 两道关。第一道在键值存储里判断有没有余票、是不是买过；第二道在数据库减库存时带「大于零」条件。**第二道是硬保险，前面判断偏了也扣不成负数。**

**Q：一人一单怎么实现？**
> 买过的用户 ID 记进一个集合，抢票前先查集合，在就提示不能重复下单。

**Q：抢票成功但订单没出现，正常吗？**
> 正常，短暂延迟。接口先返回订单号，后台排队写库，一般一两秒。一直不出现就是消费出了问题，文档里有排查方法。

# 一、登录全过程（从点「获取验证码」到后续请求带身份）

## 1.1 全景图

```
① 用户输入手机号，点「获取验证码」
        │  前端 POST /api/user/code?phone=13800000001
        ▼
② nginx 去掉 /api → 转发 127.0.0.1:8081/user/code?phone=...
        ▼
③ UserController.sendCode()
        ▼
④ UserServiceImpl.sendCode()
        ├── 生成 6 位随机验证码
        ├── 写 Redis：login:code:13800000001 = 123456，TTL 2 分钟
        └── 日志打印验证码（演示环境直接显示在页面上）
        ▼
⑤ 用户输入验证码，点「登录」
        │  前端 POST /api/user/login  {phone, code}
        ▼
⑥ UserServiceImpl.login()
        ├── 读 Redis：login:code:13800000001，和用户输入的比对
        ├── 比对失败 → 返回「验证码不一致」
        ├── 比对成功 → 按手机号查 MySQL
        │       ├── 用户不存在 → 自动注册一个
        │       └── 用户存在 → 拿出来
        ├── 生成随机 token
        ├── 写 Redis：login:token:{token} = 用户JSON，TTL 10 小时
        └── 返回 token 给前端
        ▼
⑦ 前端把 token 存起来（localStorage），后续每个请求都带
        │  请求头：authorization: {token}
        ▼
⑧ 后续任意请求进后端之前，先过拦截器
        ├── RefreshTokenInterceptor：有 token 就查 Redis
        │       ├── 查到 → 刷新 TTL 回 10 小时，用户放进 ThreadLocal
        │       └── 查不到 → 放行，但不放用户（游客）
        └── LoginInterceptor：需要登录的接口，ThreadLocal 没用户 → 返回 401
```

## 1.2 逐段拆开讲

### 第①~④步：发验证码

**前端做什么**：用户输手机号，点按钮，发 `POST /api/user/code?phone=13800000001`。

**后端做什么**（`UserServiceImpl.sendCode`）：

1. 校验手机号格式（正则）；
2. 生成 6 位随机数字；
3. **写 Redis**：key 是 `login:code:{手机号}`，value 是验证码，**TTL 2 分钟**；
4. 日志打印验证码（演示环境没接短信，验证码直接显示在页面上）。

**为什么放 Redis 不放 MySQL**：
- 验证码是**临时数据**，2 分钟就过期，放 MySQL 要定时清理，放 Redis 设个 TTL 自动就没了；
- 读验证码是**高频操作**，登录时每次都要查，Redis 内存读快。

**答辩一句话**：「验证码是临时数据，用 Redis 存并设 2 分钟过期，自动清理，不用建表。」

### 第⑤~⑥步：登录校验

**前端做什么**：用户输验证码，发 `POST /api/user/login`，body 里带 `{phone, code}`。

**后端做什么**（`UserServiceImpl.login`）：

1. **读 Redis**：`login:code:{phone}`，拿出来和用户输入的比对；
2. 不一致 → 返回「验证码不一致」；
3. 一致 → **删掉这个验证码**（防止重复使用，可选）；
4. 按手机号查 MySQL：
   - 不存在 → 自动注册一个新用户；
   - 存在 → 拿出来；
5. 生成一个随机 token（一串 UUID 之类的字符串）；
6. **写 Redis**：key 是 `login:token:{token}`，value 是用户信息 JSON，**TTL 10 小时**；
7. 返回 token 给前端。

**为什么用 token 不用 session**：
- session 存在服务器内存，多台服务器要同步，麻烦；
- token 存在 Redis，**任何一台服务器都能查**，天然支持多实例。

**答辩一句话**：「登录成功后生成 token，用户信息存在 Redis 里，设 10 小时过期，前端后续请求带着 token，后端查 Redis 就知道是谁。」

### 第⑦步：前端存 token

前端拿到 token 后存 `localStorage`，之后每个请求的请求头都带 `authorization: {token}`。

### 第⑧步：拦截器校验（每个请求都走）

**两个拦截器，顺序执行：**

| 拦截器 | 拦什么 | 做什么 |
|---|---|---|
| `RefreshTokenInterceptor` | 所有请求 | 有 token 就查 Redis，查到就**刷新 TTL 回 10 小时**，用户放进 ThreadLocal |
| `LoginInterceptor` | 需要登录的接口 | ThreadLocal 里没用户 → 返回 401 |

**为什么分两个**：
- 第一个是「**有 token 就认人，并续期**」，游客访问也能走；
- 第二个是「**必须登录才能访问**」，只拦需要身份的接口（抢票、订单、签到）。

**「续期」是什么意思**：用户登录后 10 小时内只要有操作，TTL 就刷回 10 小时，不会用着用着突然掉线。只有连续 10 小时没操作才过期。

**答辩一句话**：「拦截器拿 token 查 Redis，查到就续期并放用户进 ThreadLocal，需要登录的接口再检查一遍，没有就 401。」

## 1.3 登录涉及 Redis 的 3 个 key（背下来）

| key | 类型 | 存什么 | TTL | 谁写 | 谁读 |
|---|---|---|---|---|---|
| `login:code:{手机号}` | String | 6 位验证码 | 2 分钟 | 发验证码时 | 登录校验时 |
| `login:token:{token}` | String | 用户信息 JSON | 10 小时 | 登录成功时 | 每次请求的拦截器 |
| （续期） | — | 同一个 key | 刷回 10 小时 | 拦截器 | — |

## 2.2 按「业务功能」分组（组员更好记）

### A. 登录相关（2 个 key）

| key | 作用 | 一句话 |
|---|---|---|
| `login:code:{phone}` | 存验证码 | 「验证码 2 分钟过期，自动清理」 |
| `login:token:{token}` | 存登录状态 | 「登录后发 token，用户信息存 Redis，10 小时过期，每次请求续期」 |

### B. 抢票相关（3 个 key，核心）

| key | 作用 | 一句话 |
|---|---|---|
| `seckill:stock:{tierId}` | 余票 | 「库存放 Redis，开票瞬间高频读写」 |
| `seckill:order:{tierId}` | 已购用户 | 「买过的记进集合，再来就拦，保证一人一单」 |
| `icr:order:{日期}` | 订单号 | 「Redis 自增生成全局唯一订单号，按天分 key」 |

**这三条是答辩重点**，对应讲稿第③段「Redis 判资格」。

### C. 缓存相关（3 个 key）

| key | 作用 | 一句话 |
|---|---|---|
| `cache:show:{showId}` | 演出详情缓存 | 「热点数据放内存，不用每次查库」 |
| `lock:show:{showId}` | 缓存重建锁 | 「缓存过期时只让一个请求去查库，其他先用旧数据」 |
| 分类缓存 key | 分类列表 | 「分类不常变，缓存 10 分钟」 |

### D. 消息队列相关（不是 key，是队列）

| 名字 | 作用 |
|---|---|
| `QA` | 正常出票队列，消费者从这里取消息写订单 |
| `QD` | 死信队列，消息处理失败兜底 |

## 2.3 抢票时 Redis 的读写顺序（答辩可画）

```
用户点抢票
   │
   ▼
读 seckill:stock:{tierId}     ← 还有票吗？
读 seckill:order:{tierId}     ← 这个用户买过吗？（sismember）
   │ 都通过
   ▼
写 seckill:stock:{tierId}     ← 库存减一（incrby -1）
写 seckill:order:{tierId}     ← 用户 ID 加进集合（sadd）
   │
   ▼
写 icr:order:{日期}           ← 生成订单号（incr）
   │
   ▼
发消息到 QA 队列 → 返回订单号
```

**这五步在 Lua 脚本里一次执行完**，中间插不进别的请求，所以不会超卖。答辩被问「怎么保证原子」，就讲这一句。

## 2.4 为什么这些数据放 Redis（答辩口径）

| 数据类型 | 为什么放 Redis | 不放会怎样 |
|---|---|---|
| 验证码 | 临时、要自动过期 | 建表 + 定时清理，麻烦 |
| 登录 token | 多实例共享、要续期 | session 同步麻烦 |
| 库存 | 开票瞬间高频读写 | MySQL 行锁排队，扛不住 |
| 已购名单 | 要快速判断「在不在」 | 每次查库，慢 |
| 订单号 | 要全局唯一、自增 | 数据库自增单表有上限 |
| 演出详情 | 热点数据、读多写少 | 每次查库，数据库压力大 |

## 2.5 一条红线：Redis 里没有的东西

**订单本身不在 Redis 里。** 订单最终写 MySQL。Redis 只存「库存、已购名单、订单号、验证码、登录状态、缓存」这些**判断用、临时用、热点用**的数据。

答辩被问「订单存哪」，答：**「订单在 MySQL，Redis 只做资格判断和缓存，两者分工。」**

# 三、答辩时怎么讲（三段式）

**被问「登录怎么做的」：**
> 「手机号加验证码。验证码生成后存 Redis，2 分钟过期；登录时比对，成功后生成 token，用户信息存 Redis，10 小时过期；后续请求带 token，拦截器查 Redis 认人并续期。」

**被问「Redis 都用来干嘛了」：**
> 「四类：登录的验证码和 token；抢票的库存和已购名单；订单号自增；演出详情和分类的缓存。**核心是抢票那三个 key，库存、已购名单、订单号，开票瞬间的高频读写都在这。**」

**被问「为什么用 Redis 不用 MySQL」：**
> 「临时数据要自动过期（验证码）、高频读写要快（库存）、多实例要共享（token），这三类 MySQL 都不擅长。订单这种要长期保存的还是在 MySQL。」
